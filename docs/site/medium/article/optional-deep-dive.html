Popular validation approaches: strengths and considerations

The short comparison above groups tools by their center of gravity. That keeps the main story readable, but it hides some useful nuance. Mature teams can build excellent reusable validation with any of these approaches; the real choice is which abstraction the architecture should make easiest.

Tool or approach What it naturally owns When a policy layer adds value
Angular Template Driven Forms Simple forms expressed close to templates through directives and familiar HTML-like validation. When rules outgrow the template, repeat across workflows, or must also run outside Angular.
Angular Reactive Forms Explicit control trees, validators, observable state, nested groups, and dynamic Angular forms. When the same domain rule must survive a different control tree, application, or UI framework.
Angular Signal Forms A signal-first model with typed field access, synchronization, and schema-style validation. When an organization also has React, Vanilla TypeScript, or mature Reactive Forms consumers.
React Hook Form / Formik React form state, registration, touched/errors, submission, and resolver or schema integration. When business validation needs an identity independent of a React form instance.
Zod / Yup / Valibot Runtime parsing, shape validation, type inference, transformations, and reusable schemas. When workflow groups, required metadata, display behavior, and named domain policies sit above data shape.
Vest Readable, framework-agnostic validation suites with a test-like mental model. When a model-path policy abstraction plus first-party Angular and React adapters better matches the platform.

Angular Template Driven Forms

Template Driven Forms keep the form model close to HTML through directives such as ngModel. They are approachable, require relatively little component code, and work well for smaller forms whose validation is naturally expressed beside the input.

  • Strengths: familiar HTML-like authoring, quick setup, built-in control state, and a gentle learning curve.
  • Considerations: complex conditional rules become difficult to trace across templates; reusable cross-field logic needs directives or services; rules are naturally tied to Angular.

Angular Reactive Forms and ValidatorFn

Reactive Forms make the control tree explicit. FormControl, FormGroup, synchronous and asynchronous ValidatorFn implementations, observable state, and dynamic controls form a mature toolbox for substantial Angular applications.

  • Strengths: testable control models, strong support for nested/dynamic forms, explicit validation, and excellent Angular integration.
  • Considerations: domain rules often remain attached to Angular controls; the same policy may be reconstructed for React, Vanilla TypeScript, or another control tree; reusable factories require team conventions.
angular-reactive-validator.ts
const profileForm = new FormGroup({
  email: new FormControl('', [Validators.required, Validators.email]),
  phone: new FormControl('')
});

function contactMethodRequired(control: AbstractControl) {
  return control.get('email')?.value || control.get('phone')?.value
    ? null
    : { contactMethodRequired: true };
}

Angular Signal Forms

Signal Forms bring a signal-first mental model, automatic synchronization between form data and fields, typed field access, schema-style validation, and reactive validity/error state. They are especially interesting for new signal-oriented Angular applications.

  • Strengths: modern Angular reactivity, centralized schema functions, typed access, and field state exposed through signals.
  • Considerations: the model is Angular-specific; established Reactive Forms applications still face a migration decision; a separate abstraction remains necessary for cross-framework policy reuse.

React Hook Form

React Hook Form centers its developer experience on useForm, register, handleSubmit, and formState.errors. Its resolver ecosystem connects forms to Zod, Yup, Valibot, Vest, AJV, Joi, and other validation libraries.

  • Strengths: focused React API, performance-conscious form state, ergonomic registration, and a broad resolver ecosystem.
  • Considerations: rules commonly live in registration calls or resolver schemas; reuse outside React requires another boundary; UI lifecycle and domain policy can become coupled if the team does not separate them intentionally.
react-hook-form-style.tsx
const { register, handleSubmit, formState: { errors } } = useForm();

return <form onSubmit={handleSubmit(save)}>
  <input {...register('email', {
    required: 'Email is required',
    pattern: { value: /^[^\s@]+@[^\s@]+\.[^\s@]+$/,
      message: 'Enter a valid email address' }
  })} />
  {errors.email?.message && <p>{errors.email.message}</p>}
</form>;

Formik

Formik provides a familiar React model for values, errors, touched state, submission, field-level and form-level validation, imperative validation methods, and Yup integration.

  • Strengths: clear form-state model, synchronous and asynchronous validation, submission helpers, and well-known Yup support.
  • Considerations: validation naturally follows Formik’s React-specific values/errors/touched shape; Angular or Core-only reuse lives outside Formik.

Yup, Zod, and Valibot

Schema libraries solve the essential problem of runtime data validation. Zod emphasizes TypeScript-first schemas and inferred types; Yup offers expressive object schemas, parsing, assertions, transformations, async support, and TypeScript integration; Valibot emphasizes a modular, type-safe API built from small functions.

  • Strengths: excellent API-boundary validation, parsing of unknown data, reusable schemas, type inference, and resolver integration.
  • Considerations: a schema is not automatically a complete UI-validation system. Required indicators, touched behavior, section groups, summaries, accessible rendering, and enterprise policy naming remain application concerns.

Vest

Vest is the closest philosophical neighbor in this comparison. It uses readable suites and tests, keeps validation framework agnostic, supports focused runs and retained results, and gives careful attention to validation over time—including asynchronous behavior.

  • Strengths: test-like syntax, framework-independent suites, focused validation, and thoughtful async handling.
  • Considerations: its abstraction is suite/test oriented, whereas VRE is policy/model-path oriented and ships Angular/React adapters, required metadata, group status, messages, and summaries as one package family.
The tools can cooperate. React Hook Form can own React form state, Zod can parse an API payload, and VRE can own a reusable business policy. Architecture becomes clearer when every layer has a specific job.

Where enterprise teams often need more structure

The pressure usually appears after the first successful form: the same domain concept exists in several products; conditional requirements depend on workflow state; a wizard needs section status; a design system must render consistent summaries; different applications use different frameworks and stores; audit or QA teams need a reviewable statement of the rule.

Form-centric and schema-centric tools can support these needs through shared validators, schemas, hooks, directives, and wrappers. A policy-centric design makes the organizational unit explicit: the shared asset is a named business policy with an owner, tests, consumers, and a release history.

Form-centered boundary Policy-centered boundary
Controls or fields are the natural owners of validators. A named policy owns business validation over model paths.
Reuse is created through validator factories, shared schemas, directives, hooks, or wrappers. Reuse and composition are first-class concepts of the policy package.
Form state and validation naturally evolve together. Form state, validation evaluation, and result rendering can evolve independently.

Why policy-based validation changes application design

Policies can live at different levels

A policy should be reusable because the business concept is reusable—not because “shared” sounds architectural. Three scopes are especially useful:

  • Workflow policy: rules that belong only to a particular onboarding page, wizard, or transaction.
  • Section policy: a coherent part of a workflow, such as identity, contact, payment, or security.
  • Domain policy: a concept intentionally shared across products, such as a company-approved address or consent policy.

A customer-onboarding screen can consume all three. It might register a local AccountOnboardingPolicy, shared AddressPolicy and ConsentPolicy, and a regulated policy only when a product type requires it. On submit it validates everything; while the user moves through a wizard, it validates only the current policy group.

compose policies instead of building one mega-policy
const policies = [
  { name: 'customer', policy: new CustomerPolicy() },
  { name: 'address', policy: new AddressPolicy() },
  { name: 'consent', policy: new ConsentPolicy() },
  { name: 'onboarding', policy: new AccountOnboardingPolicy() }
];

await validation.validate(model, ['customer', 'address']);
await validation.validate(model, ['consent']);
await validation.validate(model, policies.map(({ name }) => name));

This also separates a reusable component from the business contract applied to it. An AddressComponent can always use one shared policy when every address must behave identically. Or the page can supply CustomerAddressPolicy, VendorAddressPolicy, or WarehouseAddressPolicy while the component continues to own only fields, interaction, and presentation.

Reusable policies turn repetition into architecture

Address validation illustrates the difference. Customer registration, employee profiles, vendor onboarding, warehouses, billing, shipping, and tax workflows may all need street, city, region, country, and postal-code rules. Copying those checks creates several plausible versions of the same idea. A shared AddressPolicy creates one intentionally governed version and one focused test suite.

Reuse is not automatic correctness: some workflows genuinely require different rules. Composition keeps that difference visible. A base address policy can be combined with a billing policy, while a configurable policy can target billingAddress or shippingAddress without changing the rule’s meaning.

A component can consume multiple policies

Large screens often represent several business concepts. Customer onboarding may include identity, addresses, contacts, payment, security, tax, consent, and preferences. One giant validator is hard to reason about; control-local rules hide cross-section behavior. Multiple small policies provide a middle path.

A wizard can validate the active policy group, a tab can display group status, a lazy-loaded section can register its policy when it appears, and a regulated workflow can add a policy only when the selected product requires it. Full submission can still run the complete set.

Component-owned and shared policies are both useful

Ownership model How it works When it fits
Component-owned policy The feature keeps a small policy beside its screen. The rule is specific to one workflow but benefits from policy structure and testing.
Shared component + shared policy The component always consumes the organization’s standard policy. Every consumer must enforce identical rules.
Shared component + supplied policy The component renders fields; its page supplies the business policy. The UI is reusable but validation varies by context.
Enterprise policy package A platform-owned package publishes domain policies and adapters. Several products need governed rules with independent UI ownership.

Policies as business assets

A policy can have an owner, semantic version, change log, unit tests, review rules, and known consumers. That makes a requirement such as “postal code is required for US billing addresses” discoverable without tracing templates, hooks, reducers, and schema refinements across several repositories.

This framing also improves collaboration. Product and QA can discuss the named behavior; platform teams can publish it; application teams can choose display and interaction; security and backend teams can identify which server-side controls remain authoritative.

Separation of concerns: UI, component, policy, engine, and domain rule

  1. UI: markup, accessible relationships, focus, colors, placement, and summaries.
  2. Component: edits the model and decides when feedback should be shown.
  3. Policy: names the model paths, conditions, messages, and business expectations.
  4. Engine: registers policies, executes validators, and returns normalized results and metadata.
  5. Domain service: owns complex decisions or remote data that should not be buried in a validator.

Architectural flexibility without prescribing one model

These boundaries allow architecture to change independently. A product can replace local state with NgRx or Redux Toolkit, move from Bootstrap to a design system, or add another UI host without rewriting the policy itself. VRE does not require one form library, component system, state store, or application architecture around Core.

What the packages—and your application—own

Layer Responsibility Should not own
@validation-rules-engine/core Policies, validators, execution, result models, required/touched metadata, groups, and utilities. Angular directives, React hooks, product markup, or store reducers.
@validation-rules-engine/angular Angular directives, services, display strategies, status components, summaries, and lifecycle integration. The organization’s business rules or permanent design-system decisions.
@validation-rules-engine/react Provider, engine integration, form and field hooks, messages, summaries, and React lifecycle integration. Redux state ownership or rules that should also run outside React.
Your domain package Shared policies, custom business rules, naming conventions, tests, and release governance. Page-specific rendering and interaction.
Your application or design system When to reveal errors, accessible markup, focus behavior, layout, colors, summaries, and store subscriptions. Duplicated copies of the same cross-product business rule.

That last row matters. Required markers may appear immediately, while an error should often wait until blur or submit. A summary may move focus after a failed submit. A section badge may validate one group without revealing every future step. These are user-experience decisions, so the host keeps them even when policy evaluation is shared.

UI error rendering is fully customizable

Validation evaluation produces data: property paths, validity, messages, required metadata, touched metadata, policy/group status, and summary entries. Rendering translates that data into a product experience. Keeping those jobs separate lets the same result feed an inline message, an accessible summary, a tab badge, a disabled action, or telemetry without teaching the policy about markup.

Rendering flow

  1. The policy produces normalized results and metadata for model paths.
  2. The adapter connects those results to the host’s lifecycle and observation model.
  3. A display strategy decides when feedback is eligible to appear.
  4. Built-in or custom components render inline messages, summaries, required markers, and group status.
  5. The application owns focus, accessible relationships, visual design, and product-specific interaction.

Angular rendering customization

Angular applications can use supplied directives, services, display strategies, message components, summaries, and status components. A display strategy can decide whether an error waits for touch, blur, or submit. Teams can also bind results into Angular Material, Bootstrap, Tailwind, or an internal component library and keep the policy unchanged.

React rendering customization

React applications can use the provider, form and field hooks, field helpers, message components, and summaries. Or a design-system field can read the same hook state and render its own labels, descriptions, error regions, and focus behavior. The hook connects lifecycle; the component retains presentation ownership.

Ready-to-use UI components without locking into them

Option 1: use built-in rendering

Start quickly with supplied messages, summaries, required metadata, and group/status components. This is useful for prototypes, internal tools, and teams that want consistent defaults.

Option 2: replace rendering

Feed normalized results into a company design system. Keep product-specific markup, accessibility behavior, animation, layout, and styling local.

“Ready to use” and “customizable” are not opposites. A framework adapter can provide a productive default while Core keeps the result model independent enough for a replacement renderer.

UI framework agnostic by design

Framework independence applies to Core policies, not to lifecycle code. Angular directives, React hooks, and direct DOM handlers should look different because their hosts are different. They converge on the same model paths, policy names, validators, and result vocabulary.

Framework adapter architecture

Host Adapter responsibility Reusable asset
Vanilla TypeScript Call Core, observe DOM events, and render results directly. The same framework-free policy and Core result model.
Angular Connect controls, directives, services, display strategy, and change detection.
React Connect providers, hooks, component state, effects, and rendering.

Consuming Core with Vanilla JavaScript or TypeScript

The Core package can be used without a UI adapter. Install @validation-rules-engine/core, build validators from a policy, execute them against a plain model, and render validationResults wherever the application needs them. That makes Core useful for browser pages, Node utilities, prototypes, tests, and non-framework hosts.

core-only sketch
import { ValidatorHelper } from '@validation-rules-engine/core';
import { CustomerProfilePolicy } from './customer-profile.policy';

const helper = new ValidatorHelper();
const validators = new CustomerProfilePolicy()
  .addValidations(helper);

const model = {
  firstName: '',
  email: 'not-an-email',
  validationResults: [] as unknown[]
};

// Evaluate the validators for their model paths, write the normalized
// results to model.validationResults, then render them in the DOM.
// The Vanilla showcase demonstrates blur, submit, summary, and ARIA wiring.

Angular and React add lifecycle convenience; they do not redefine the policy. The live Vanilla, Angular, and React showcases let you compare those consumption styles side by side.

Extensible through TypeScript

Built-in validators cover common mechanics. Organization-specific decisions can use a small custom rule, and repeated concepts can be parameterized with model paths. The goal is not cleverness; the goal is a policy that a reviewer can still read as a business statement.

Custom business rule example

loan.policy.ts
helper.validateFor('loan.amount')
  .isRequired('Loan amount is required')
  .userDefined(
    'Loan amount exceeds the approved limit',
    (model, value, message) =>
      Number(value) <= Number(model.loan.approvedLimit)
        ? true
        : { message }
  );

A custom rule should remain small and readable. If it grows into eligibility logic, orchestration, or remote access, call a tested domain helper or service rather than turning the policy into a second application layer.

Reusable policy with configurable paths

configurable-address.policy.ts
export class ConfigurableAddressPolicy implements ValidationPolicy {
  constructor(private readonly prefix = 'address') {}

  addValidations(helper: ValidatorHelper): Validator[] {
    const path = (field: string) => `${this.prefix}.${field}`;

    return [
      helper.validateFor(path('street'))
        .isRequired('Street is required'),
      helper.validateFor(path('postalCode'))
        .userDefined('Postal code is not serviceable',
          (model, value, message) =>
            isServiceable(model, value) ? true : { message })
    ];
  }
}

const billing = new ConfigurableAddressPolicy('billingAddress');
const shipping = new ConfigurableAddressPolicy('shippingAddress');

Configurable model-path prefixes let the same concept target billing and shipping addresses without duplicating rules. Keep the path factory obvious so the policy still explains itself during code review.

Enterprise customization: shared policies, local presentation

A large organization may maintain a shared policy library, a validation-platform wrapper, several Angular and React products, a Vanilla TypeScript utility, and more than one design system. Consistency does not require every application to draw the same red border. It requires agreement about which layer owns which decision.

Enterprise concern Policy-centric support Practical outcome
Consistency Shared domain policies define repeated business validation once. Intended consumers enforce the same business meaning.
Local UI ownership Applications render normalized results with built-in or custom components. Products keep their design systems without forking rules.
Maintainability Named policies have focused tests, owners, and versions. Rule changes are easier to review and roll out.
Cross-framework operation Core policies are consumed through Angular, React, or Core-only hosts. Platform teams avoid inventing a policy language for each framework.
Future change Adapters isolate framework lifecycle and presentation. Store, component-library, or framework changes cause less policy churn.

Some organizations wrap the packages in an internal module such as @company/validation-platform. That wrapper can provide default display behavior, approved policy packages, telemetry hooks, and adapter setup while still exposing escape hatches for individual products.

Why Validation Rules Engine was created

VRE was created for cases where validation rules need to be explicit, named, reusable, and independent of any single UI implementation—but teams still want practical Angular and React integrations rather than an engine they must wire from scratch.

It is not an instruction to abandon Angular Forms, React form libraries, schemas, or local validation. It adds a policy layer when the business rule needs a longer lifespan and a wider audience than one form instance.

Core design principles

Policy first

Business rules live in named policies instead of being scattered across templates, hooks, reducers, and callbacks.

Framework adapters

Each host remains idiomatic while consuming the same Core concepts.

Plain model paths

Rules target model properties, including nested objects and reusable prefixes.

Display is separate

Validation results are data; inline messages, summaries, classes, and required markers are presentation.

Groups matter

Large workflows need section validation, status, summaries, submit checks, and programmatic execution.

No universal claims

The design optimizes for reusable validation architecture, not for winning every form-validation comparison.

Real examples and the end-to-end validation flow

The same CustomerProfilePolicy can validate a plain object in Core, be registered under a policy name in Angular, and be supplied through a React provider. The property path and rule remain identical; only the host’s lifecycle bridge changes.

  1. A user edits a model through an Angular control, React field, or DOM input.
  2. The host decides that validation should run—for example on blur, group navigation, or submit.
  3. The adapter or Core-only engine executes the selected named policies against the plain model.
  4. Core produces normalized results plus required, touched, policy, and group metadata.
  5. The host updates inline messages, summaries, section status, ARIA relationships, and focus using its own rendering approach.

This flow explains why the policy can remain stable when a team replaces local component state with a store or replaces one component library with another. Model delivery and result rendering change around the policy rather than inside it.

State stores and asynchronous rules

NgRx and Redux Toolkit are useful examples because their architectural pressure is obvious: reducers must remain predictable, selectors should derive state, and side effects belong in effects, thunks, listeners, or services. The validation policy should not become a reducer and the reducer should not restate the policy.

  1. Select or receive the current plain model from the store.
  2. Run the named policy through Core or the framework adapter.
  3. Expose the resulting validation state through the application’s existing observation mechanism.
  4. Keep display decisions in the field, component, or design-system layer.

The same pattern generalizes to NGXS, Signals, Zustand, Jotai, MobX, RxJS stores, and local component state. Only the subscription and update APIs change. For asynchronous rules, add cancellation, a request token, or latest-value checks so a slow response for an older value cannot overwrite the result for the value the user sees now.

A low-risk adoption checklist

  1. Choose one rule already duplicated across two screens. Do not begin with the whole application.
  2. Write a framework-free policy and focused unit tests for its conditions, paths, and messages.
  3. Connect one host and agree on touched, submit, required-marker, summary, and accessibility behavior.
  4. Reuse the policy in a second screen or framework. Measure whether the shared ownership actually reduced drift.
  5. Only then define naming, package ownership, versioning, and policy-composition conventions for the wider organization.

Stop if the abstraction makes a tiny form harder to understand or if no genuine reuse appears. Continue when the policy becomes easier to review, test, and evolve than its duplicated alternatives. And keep the security boundary explicit: browser validation helps users; the server must still authorize actions, validate untrusted input, and enforce persistence constraints.

When another tool may be the better fit

Primary need Likely starting point Why
A small Angular-only form Template Driven, Reactive, or Signal Forms Angular already provides the form lifecycle and validation surface.
A React form with no cross-host policy requirement React Hook Form or Formik The form-state developer experience is the main problem to solve.
Parsing unknown input or validating an API contract Zod, Yup, Valibot, or JSON Schema tooling Runtime shape, parsing, transformation, and type inference are central.
Framework-agnostic validation with a suite/test mental model Vest Its suite syntax and execution model may match the team naturally.
Named domain policies reused across Angular, React, and Core-only hosts Validation Rules Engine Policy composition, model paths, result metadata, and adapters are the intended design center.

What Validation Rules Engine is not claiming

  • It is not claiming that every form needs a policy layer.
  • It is not a replacement for server-side validation, authorization, sanitization, database constraints, or API-boundary parsing.
  • It does not eliminate host integration; Angular, React, and Vanilla lifecycles remain different.
  • It does not require every policy to be global. Local, shared, supplied, and composed policies are all valid.
  • It does not prevent teams from using Angular Forms, React Hook Form, Formik, Zod, Yup, Valibot, or Vest alongside it.
